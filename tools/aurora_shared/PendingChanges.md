## Model Validation and Contracts

These rules are derived from the canonical instruction and schema files under `.github/agents/aurora/`.

### `$schema` resolution

- For JSON files that include `$schema`, resolve it relative to the JSON file’s location on disk.
- Fail with a clear error when `$schema` is missing or points to a non-existent schema.
- Consider additionally verifying that `$schema` resolves to the expected schema file for that artifact type (card vs compact vs reference registry).

### NDJSON audit log

- `AuditLog.ndjson` MUST be treated as append-only, line-delimited JSON.
- Validation must be per-line (one JSON object per line).
- Error reporting should include:
	+ Mission id (folder)
	+ Filename
	+ 1-based line number
	+ A short, user-actionable message

### Graph invariants and semantic validation

- Enforce the invariant rules from `Aurora.instructions.md` when validating a model:
	+ The model contains exactly one `Mission` card.
	+ The `Mission` card is the root vertex and has out-degree only.
	+ All non-`Mission` cards are reachable from `Mission` (no orphans).
	+ Traversal algorithms halt when encountering a leaf (out-degree `0`) or a previously visited node.
- Validate that every link target refers to an existing card id.
- Validate link relationship semantics using `reference/Aurora.canonical.definitions.json` where possible.
	+ At minimum, ensure that relationship verbs used in links exist in the relationship registry.
	+ Clarify whether non-canonical card types may use arbitrary relationship verbs, or whether all relationships must be present in the registry.

### Compact model

- `Compact.json` MUST validate against `Aurora.compact.schema.json`.
	+ Document root requires `$schema` and `cards`.
	+ Each compact card requires `attributes` (even if empty).
	+ Compact cards omit `description` (do not assume it exists when rendering from a compact export).

### Appearance definitions

- `Aurora.appearance.json` entries may omit `icon`.
	+ If `icon` is present, it MUST be a non-empty string.
	+ Renderer should treat missing `icon` as “no icon” (do not substitute an empty string).

## View Generation

Views are generated by selecting a set of card-type acronyms as roots for local graphs, selecting a set of other card-type acronyms to include when traversing from the roots, and rendering a diagram showing those cards and the links between them. Views **do not change the model**; they change what part of and how the model is viewed. One model, many views.

Cards that share the same `boundary` value should be rendered grouped in a dashed rectangle with the name of the boundary top-center.

If a card has a `notes` property it should be rendered as a callout using the "curly-braces" symbol and linked from the card using a dotted edge.
	+ Notes callouts are view-only render artifacts (they are not cards and they do not participate in traversal).

### View roots and traversal

- `root_card_types` and `included_card_types` are 3-letter acronyms (for example `MIS`, `REQ`, `COM`) as used by `View.Definitions.json`.
	+ Prefer deriving a card’s acronym from its `id` prefix (for example, `REQ-001` -> `REQ`), and optionally cross-check against `Aurora.canonical.definitions.json` for canonical card types.
- Traversal always starts from each root and (by the invariants) continues away until either reaching a leaf or closing a local loop.
	+ Track visited card ids to prevent infinite traversal.
- Links are not filtered for general traversal.
	+ Traverse all outgoing links regardless of relationship verb.
- When rendering a view, root cards are always rendered.
- During traversal, a non-root card is eligible to be rendered if its card-type acronym is in `included_card_types`.
	+ No nodes or edges outside the rendered cards (and the links between them) are rendered.
	+ Clarify whether traversal is allowed to “pass through” excluded card types to reach included types, or whether excluded types terminate that branch.

### Symbol Scaling and Layout

- Use a 16px font-size and 1.2 line-height.
- All of the symbols have been redrawn. The symbols in the `svgtemplate.txt` file are scaled (720 x 450) to fit 80 characters wide and 20 lines high. They should not need to be resized or scaled.
- Update the placement calculations based on the fixed size of the shapes.
	+ The gap should be 80 px (minimum) horizontal and vertical.
	+ The space between adjacent lines should be 8 px.
- The icon should be centered and baseline aligned at 16,249, and 48px tall.
	+ Clarify whether `16,249` is intended to be an `(x,y)` coordinate, and if so whether `x=16` means “left inset” or “center point”.
- The first line of text should be centered and baseline aligned at 400,40 relative to the top-left of the symbol.
	+ Clarify whether `400,40` is intended to be an `(x,y)` coordinate.
- Text should be wrapped at spaces (if possible) to fit the width.
- The text should have the following lines:
	+ {id}: {card_type} ({card_subtype})
	+ <strong>{name}</strong>
	+ {blank line}
	+ {description, wrapped}
	+ ...
	+ Clarify rendering when `card_subtype` is empty/missing (for example, omit parentheses entirely).

## Questions and Clarifications (to resolve before implementation)

- Model home reference folder name is `reference/` (singular) in the canonical instructions.
	+ Is that definitive for all tooling (CLI/editor/shared), or should `references/` also be supported for backwards compatibility?
- Views use card-type acronyms (`MIS`, `REQ`, etc.). Should aurora_shared treat the acronym as:
	+ Always derived from the card `id` prefix, or
	+ Derived from `card_type` via `Aurora.canonical.definitions.json` (and if so, what is the rule for non-canonical types)?
- Traversal rule ambiguity: if a node is excluded (not in `included_card_types` and not a root), does traversal stop at that node, or can traversal continue through it without rendering it?
- Notes rendering: should `notes` be rendered even if it is only whitespace after trimming?
- Boundary grouping: should empty/whitespace `boundary` values be treated as “no boundary”, and are nested boundaries a thing or are boundaries always flat labels?
