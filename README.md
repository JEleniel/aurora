# Agent-Unified Representation of Requirements and Architecture (AURORA)

AURORA is an architectural practice and tools designed to be equally followable by both machine and human agents. AURORA defines a rigorous, MBSE-class architectural modeling framework designed for symmetric readability by human engineers and autonomous agents. It provides a lightweight but complete representational schema that captures requirements, behavior, structure, interfaces, constraints, and traceability in a single, coherent model. The objective is a common architectural language that supports automated reasoning, validation, and lifecycle tooling while remaining directly interpretable by expert practitioners.

Because it is designed to be readable by machine agents as well as humans, AURORA artifacts can be generated by machine learning models, consumed by coding agents, and used to automatically generate views of the architecture.

## Status

> AURORA — both the specification and the reference tooling — is currently in pre-release. A CHANGELOG and other release tracking will be added for v1.0.0.

## Goals

- **Unified Semantics:** One representation equally usable by humans and machine agents.
- **Complete Architectural Coverage:** Operational, logical, physical, and behavioral modeling with complete traceability.
- **Tool-Agnostic Implementation:** Simple to adopt, serialize, and integrate into existing systems.
- **Automated Reasoning Compatibility:** Schema designed for constraint solvers, LLMs, static analyzers, and agents.
- **Human-Centric Readability:** Clear structure and terminology without sacrificing formal rigor.
- **Universal Formats:** All documents use JSON and accompanying JSON Schemas are provided.
- **Complete Provenance and Traceability:** Every action on a card is logged on the card, providing a complete audit trail.
- **Secure Design Options:** Support for cryptographic signatures and checksums enables secure documents. Because all documents are JSON, they can be encrypted and decrypted by tooling.
- **Interactive Exploration:** Navigate and understand complex architectures through centered element views with related links and dependencies displayed at a glance.

## Core Concepts

AURORA models are intentionally simple, explicit, and link-relationship-centric so that both human practitioners and automated agents can read, reason about, and act on the same architectural artifacts.

### Everything is an Element

- Everything in the architecture — drivers, requirements, deployments, zones — is represented by a card that captures every detail of the element.
- CDO: link to a complete list of the Elements defined in the architecture; this should be part of the docs.

### Elements have Relationships

- Every element in the model is connected to _at least_ one other, allowing fully automated view generation.
- Links are directional, first-class relationships that point toward the Root Driver. All links form a derivation hierarchy rooted at the Root Driver.
- Links themselves have no intrinsic semantic type; their meaning is derived from the current view. In a requirements view a link means "satisfies"; in a component view it means "implements"; in a traceability view it means "traces-to". This view-dependent semantics enables flexible interpretation of the same model across different perspectives.

## Machine-Agent Integration

- Deterministic serialization (JSON) and an agreed minimal ontology make models unambiguous for agents and tools.
- Models map naturally into graph structures (nodes + typed edges) for reasoning engines, search, and graph queries.
- Validation tooling verifies syntactic schema conformance, constraint satisfaction, and trace completeness; reasoning tools can run invariants, safety checks, and automated impact analysis.
- A cross-platform reference toolset is included here supporting card creation, management, and lifecycle operations.

## Tooling Capabilities

### Card and Link Management

- Create, edit, and manage Cards representing any Element type (Drivers, Requirements, Behaviors, Interfaces, Constraints, and more).
- Define and manage Links with typed relationships that preserve intent and enable rich queries.
- Validate cards against schemas and cross-check link integrity across the model.
- Maintain complete provenance with audit trails for every change.

### Multi-Perspective Views

- Generate views of your architecture from standard perspectives: logical components, physical deployment, operational behavior, stakeholder actors, and requirement traceability.
- Views are automatically derived from the card-and-link model; no separate maintenance required.
- Tabular and graph-based queries support custom analysis across the entire model.

### Interactive Exploration

- Select any Element and center it on the screen with its related links and connected Elements displayed in context.
- Explore dependencies, relationships, and impact chains through an intuitive, graph-centric interface.
- Navigate upstream to requirements and drivers or downstream to implementation and deployment with a single gesture.

## Human–Machine Collaboration

- Authoring workflows support both hand-edited text and generated artifacts (templates, inferred links, and suggested refinements from analysis agents).
- Change records and provenance are preserved to support review, approval, and audit trails; agents can propose changes while humans accept, reject, or refine them.

## Representation

**Cards** are the core way of representing Elements in the model. A Card is just a JSON data file containing all the details of that Element. This project adopts a strict "one Element = one Card" approach: every atomic architectural entity is represented as a single card. Cards are lightweight, self-contained artifacts that map directly to machine-friendly data structures and human views.

**Links** represent directional relationships between Cards. Links always point toward the Root Driver, forming a derivation hierarchy. Every Card MUST have at least one Link with the exception of the Root Driver. The semantic meaning of a link is context-dependent and is determined by the view or analysis tool interpreting the model.

## The Model

- Every model starts with a "Root Driver": a single card representing the project's mission or authoritative source. Every other card MUST be linked (directly or indirectly) to the Root Driver via directional links that point toward it, forming a complete derivation hierarchy that preserves provenance and intent. This convergence toward Root guarantees connectivity and enables complete traceability.
- No multi-page monoliths: Focus is on what the architecture contains and how it connects.
- One Element = One Card: Each Element exists only once in the model, represented by a single card, and each card represents exactly one element.
- Views are projections; the canonical information always lives on the card. Typical architectural views can be automatically generated at any level. No need to spend valuable time on layouts and styles; focus on the architecture.
- Links enable traceability and queryability. The Element/Relationship graph enables highly flexible queryability, including tabular, graph, and centered-element exploration modes.
- All Cards are JSON, all Elements are represented by Cards, and all possible Elements can be represented. While many Element types and related cards are provided, the schema supports easy extension to add any type of Element or Relationship desired. Cards are stored as JSON and displayed in a human-readable, editable form.

> Note: JEleniel, the original author of this spec, chose JSON over more "human readable" formats such as YAML because the explicit delineation of JSON makes documents more resilient to both machine and human error. Anyone who has edited a complex YAML document without an IDE will understand why.
