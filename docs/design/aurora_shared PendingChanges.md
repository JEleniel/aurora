# Pending Changes to aurora_shared and aurora_cli

## Purpose and Scope

This document defines the required, target-state changes for `aurora_shared`. Treat each bullet as an implementation requirement and acceptance criterion. These instructions are intentionally implementation-focused so work can be completed directly from this document without additional interpretation.

## Loading Models

- Ensure that all required schema files and reference files exist (and are readable) in the correct locations under the model home. If any are missing log an error and exit.
- Load the reference files from disk (model home), not compiled-in defaults.
	+ Reference folder name is `reference/`.
	+ Reference files:
		* `reference/Aurora.appearance.json`
		* `reference/Aurora.canonical.definitions.json`
		* `reference/View.Definitions.json`
	+ Schema folder name is `schemas/`.
	+ Schema files:
		* `schemas/Aurora.appearance.schema.json`
		* `schemas/Aurora.audit.schema.json`
		* `schemas/Aurora.canonical.definitions.schema.json`
		* `schemas/Aurora.card.schema.json`
		* `schemas/Aurora.compact.schema.json`
		* `schemas/View.Definitions.schema.json`
- Validate and check each model on load.

### Validation

#### `$schema` resolution

- All JSON data files MUST include the `$schema` property. It SHOULD be the relative path to the appropriate schema in the model home `schemas/` folder.
	+ If `$schema` is missing log an error, finish validating the models, and exit. This will allow all errors to be identified in a single pass.
	+ Do not fail on `$schema` path errors. If `$schema` does not resolve or resolves to the wrong schema type for the artifact being validated: log a warning and validate against the correct schema anyway.
- The NDJSON files have an associated schema as well, but do not include the `$schema` property. Validate them against their associated schema.
	+ `AuditLog.ndjson` validates against `schemas/Aurora.audit.schema.json`

#### Graph invariants and semantic validation

- Enforce the invariant rules from `Aurora.instructions.md` when validating a model:
	+ The model contains exactly one `Mission` card.
	+ The `Mission` card is the root node and has out-degree only.
	+ All non-`Mission` cards are reachable from `Mission` (no orphans).
	+ Traversal algorithms halt when encountering a leaf (out-degree `0`) or a previously visited node.
- Validate that every link target refers to an existing card id.
- Validate card id acronym consistency.
	+ For canonical card types: the card id prefix MUST match the canonical acronym from `reference/Aurora.canonical.definitions.json`.
	+ For non-canonical card types: derive the acronym from the card id prefix.
		* Inconsistent acronyms for the same non-canonical `card_type` are a validation failure.

### Checking the Models

- Canonical registry checks are checks, not validity gates.
	+ A model is valid whether it uses canonical cards/relationships or not, as long as it meets the invariants above.
	+ Log warnings for unknown card types, unknown relationship verbs, or unknown relationships.
	+ Do not fail validation solely due to non-canonical card types or non-canonical relationship verbs.

## View Rendering

Views are generated by selecting a set of card-type acronyms as roots for local graphs, selecting a set of other card-type acronyms to include when traversing from the roots, and rendering a diagram showing those cards and the links between them. Views **do not change the model**; they change what part of and how the model is viewed. One model, many views.

Never render anything that resolves to only whitespace after trimming.
	+ This applies to boundary labels, note callouts, subtype display, and any text content.

Cards that share the same `boundary` value should be rendered grouped in a dashed rectangle with the name of the boundary top-center.
	+ Boundaries are primarily view-only logical groupings.
	+ Nested boundaries are supported using dot notation (for example, `Security.Auth` is a child of `Security`).
		+ Render nested boundary groups as nested dashed rectangles.
		+ Boundary labels render only the final segment of the boundary path.
			- For `Security.Auth`, render `Auth` as the label for that boundary group.
	+ `boundary` values that are empty or whitespace are invalid.
		* Log a warning and ignore the boundary for grouping purposes.

If a card has a `notes` property it should be rendered as a callout using the "curly-braces" symbol and linked from the card using a dotted edge.
	+ Notes callouts are view-only render artifacts (they are not cards and they do not participate in traversal).

### View roots and traversal

- `root_card_types` and `included_card_types` are 3-letter acronyms (for example `MIS`, `REQ`, `COM`) as used by `View.Definitions.json`.
	+ Filtering is based on the card id prefix (no translation from `card_type` is required).
	+ Canonical acronyms come from `reference/Aurora.canonical.definitions.json`.
		* Unknown acronyms are derived from the card id prefix.
		* Inconsistent extended acronyms (for the same non-canonical `card_type`) are a validation failure.
- Non-canonical card types are the reason view definitions are data files.
	+ Users MUST provide view definitions that include their custom card acronyms.
	+ If the model contains custom acronyms that do not appear in any view definition, log a warning.
- Traversal always starts from each root and (by the invariants) continues away until either reaching a leaf or closing a local loop.
	+ Track visited card ids to prevent infinite traversal.
- Links are not filtered for general traversal.
	+ Traverse all outgoing links regardless of relationship verb.
- When rendering a view, root cards are always rendered.
- During traversal, a non-root card is eligible to be rendered if its card-type acronym is in `included_card_types`.
	+ No nodes or edges outside the rendered cards (and the links between them) are rendered.
	+ If a node is excluded, stop traversal at that node.

### Fixed Symbol Geometry and Layout

- Use a 16px font-size and 1.2 line-height.
- Dynamic scaling is removed. Do not dynamically scale symbols or icons at render time.
- All symbols have been redrawn and normalized in `assets/references/SVGTemplate.svg`.
	+ Use the native symbol geometry (720w x 450h) directly.
	+ Placement calculations MUST assume fixed symbol dimensions.
	+ The gap should be 160 px (minimum) horizontal and vertical. Use the same gap universally for a given axis.
	+ The space between adjacent lines should be 8 px.
- The top left of the icon should be at 70x,218y and the icon should be scaled to 72px x 72px.
- The first line of text should be centered and baseline aligned at 398x,100.2y relative to the top-left of the symbol.
- Text should be wrapped at or before 80 characters, at spaces if possible.
- The text should have the following lines:
	+ `id`: `card_type` (`card_subtype`)
	+ <strong>{name}</strong>
	+ {blank line}
	+ {description, wrapped}
	+ ...
- Omit the parenthesis and additional spaces from the text if `card_subtype` is not present.
- Icons are no longer Unicode characters due to rendering issues with some tools. Render them as fixed `<use ...>` references.

### Edge Routing

- Edges that go to the same destination may be combined to simplify the view.
- Edges that do not go to the same destination MUST NOT overlap.
- When two edges cross, the horizontal edge should have a jump (half circle) over the vertical edge.
- Edges may travel in any of the eight cardinal directions.
- The first and last 40px of an edge must point orthogonal to the symbol.
- Arrowheads should be 20px.
- Edges should not be closer than 40px to a symbol unless originating or ending at the symbol. (Symbols have a 40px margin.)
- Edges MUST NOT cross the 720w x 450h boundary of a symbol.

## aurora_cli Parity Addendum

To bring `aurora_cli` fully up to date with the latest canon, implement the following CLI-specific requirements in addition to the `aurora_shared` updates above.

- Define and document the CLI contract for `validate`, `render-views`, `render-all`, and `compact`.
	+ For each command, specify required inputs, validation gates, generated outputs, and canonical output paths.
- Enforce the view root safety rule from `REQ-007`.
	+ View roots MUST exclude cards participating in cycles.
- Define a diagnostics contract for CLI runs.
	+ State what is logged/emitted for load failures, validation errors, registry warnings, render failures, and compact export failures.
	+ Warning-only runs MUST return exit code `0` (success, no error).
- Align command help and user-facing wording with current canon terminology.
	+ Remove outdated wording (for example, references to "tabular relationship views" when diagram rendering is intended).
- Add end-to-end CLI acceptance tests that verify canonical behavior.
	+ Include tests for model-home `schemas/` + `reference/` loading, NDJSON audit semantics, acronym-based view filtering, and fixed-geometry SVG rendering behavior.
