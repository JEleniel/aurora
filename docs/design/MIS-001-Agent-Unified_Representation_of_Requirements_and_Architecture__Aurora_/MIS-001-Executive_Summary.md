# MIS-001 Executive Summary

This executive summary captures the mission intent plus 3 drivers and 13 requirements.

## Mission

- **ID:** `MIS-001`
- **Name:** Agent-Unified Representation of Requirements and Architecture (Aurora)
- **Description:** A rigorous, MBSE-class architectural modeling framework designed for equal readability by human engineers, machine learning ("AI") agents, and computer programs. It provides a lightweight but complete representational schema that captures requirements, behavior, structure, interfaces, constraints, and traceability in a single, coherent model. The objective is a common architectural language that supports automated reasoning, validation, and lifecycle tooling while remaining directly interpretable by expert practitioners. Because it is designed to be readable by machine agents as well as humans, Aurora artifacts can be generated by machine learning models, consumed by coding agents, and used to automatically generate views of the architecture.

## Drivers

- `DRI-006` — Deterministic Architectural Language. Enable unambiguous interpretation and automated reasoning by enforcing deterministic model structure and traversal rules rooted at the Mission card.
- `DRI-007` — Machine and Human Readable Source of Truth. Ensure Aurora models remain directly interpretable by expert practitioners while staying friendly to machine parsing, tooling, and agent consumption.
- `DRI-008` — Canonical Registries and View Definitions. Provide a stable, shared vocabulary for cards, relationship verbs, and views so validation and rendering can be deterministic and portable across tools.

## Requirements

- `REQ-016` — Strict JSJSON Card Encoding. Aurora card files SHALL be stored as strict JSON (RFC 8259) using the .jsjson extension: double quotes, no comments, no trailing commas, UTF-8 encoding, and exactly one trailing newline.
- `REQ-017` — Identifiers, Filenames, and Model Layout. Aurora cards SHALL use stable identifiers (e.g., MIS-001) that MUST NOT change once issued. Card files SHALL be named <id>-<Sanitized_Name>.jsjson, where special characters are stripped and spaces are replaced with underscores. Models SHALL follow the Model Home and Mission folder layout conventions so tools can discover, validate, and render deterministically.
- `REQ-018` — Single Root Mission. Each Aurora model SHALL start with exactly one Mission card that serves as the root of the directed graph. The Mission card SHALL only have outgoing links and SHALL provide a consistent starting point for traversal and view generation.
- `REQ-019` — Directed Graph with Local Cycles. All Aurora links SHALL lead away from the Mission card. Local cycles MAY exist within bounded subgraphs (for example state machines) as long as no link creates a path back to the Mission.
- `REQ-020` — Boundary and Note Semantics. Boundary cards SHALL be used to group related cards for rendering and navigation; they may have a subtype such as End to limit recursion. Note cards SHALL be used only as annotative leaves (incoming links only) and SHALL NOT introduce new structural model elements.
- `REQ-021` — Canonical Card Registry. Aurora tooling and documentation SHALL use a canonical registry of card types (and optional subtypes) to support consistent rendering, validation, and communication across tools.
- `REQ-022` — Canonical Relationship Registry. Aurora tooling and documentation SHALL use a canonical registry of relationship verbs, including allowed source and target card types, to enable deterministic validation and interoperable views.
- `REQ-023` — Canonical View Registry. Aurora tooling and documentation SHALL use a canonical registry of view definitions that declare which card types are included and what root types anchor each view.
- `REQ-024` — Schema Referencing Rules. All Aurora card files SHALL include a $schema field referencing the applicable Aurora schema using a relative path from the card file to the Model Home schema file.
- `REQ-025` — Model Integrity Validation. Aurora models SHALL be machine-validatable for integrity: every non-Mission, non-Note card SHALL have at least one incoming link; every card SHALL be reachable from the Mission; and all links[].target values SHALL reference an existing card id.
- `REQ-026` — Views as Projections. Views SHALL be treated as projections of a single underlying model graph by selecting a set of card types (and optional subtypes) and rendering only those cards and the links between them; views SHALL NOT change the underlying model.
- `REQ-027` — Audit Trail and Versioning. All Aurora cards SHALL include an audit_trail with a per-card SemVer version, an optional SHA256 hash (nullable), and a chronological history of created/edited/deleted events including editor identity and RFC3339 timestamps.
- `REQ-028` — Semantics Derived from Invariants. Aurora card and relationship labels SHALL be treated as descriptive metadata; the meaning of the architecture SHALL be derived from the model’s invariant rules and the current view’s inclusion/projection of card types and links.
