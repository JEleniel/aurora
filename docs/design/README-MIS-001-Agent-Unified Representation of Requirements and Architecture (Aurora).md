# MIS-001: Agent-Unified Representation of Requirements and Architecture (Aurora)

**[Mission Card](MIS-001-Agent-Unified Representation of Requirements and Architecture (Aurora).md)**

A rigorous, MBSE-class architectural modeling framework designed for equal readability by human engineers, machine learning ("AI") agents, and computer programs. It provides a lightweight but complete representational schema that captures requirements, behavior, structure, interfaces, constraints, and traceability in a single, coherent model. The objective is a common architectural language that supports automated reasoning, validation, and lifecycle tooling while remaining directly interpretable by expert practitioners.

Because it is designed to be readable by machine agents as well as humans, Aurora artifacts can be generated by machine learning models, consumed by coding agents, and used to automatically generate views of the architecture.

### ADR

- **[ADR-002 - Strict JSJSON Canonical Storage](MIS-001/ADR/ADR-002.md)**: Decision: Aurora cards are stored as strict JSON using the .jsjson extension. Rationale: deterministic diffs, wide tool compatibility, and unambiguous machine parsing. Trade-off: no comments; humans must rely on explicit fields and Notes instead.

### Requirement

- **[REQ-028 - Semantics Derived from Invariants](MIS-001/Requirement/REQ-028.md)**: Aurora card and relationship labels SHALL be treated as descriptive metadata; the meaning of the architecture SHALL be derived from the model’s invariant rules and the current view’s inclusion/projection of card types and links.

- **[REQ-016 - Strict JSJSON Card Encoding](MIS-001/Requirement/REQ-016.md)**: Aurora card files SHALL be stored as strict JSON (RFC 8259) using the .jsjson extension: double quotes, no comments, no trailing commas, UTF-8 encoding, and exactly one trailing newline.

- **[REQ-023 - Canonical View Registry](MIS-001/Requirement/REQ-023.md)**: Aurora tooling and documentation SHALL use a canonical registry of view definitions that declare which card types are included and what root types anchor each view.

- **[REQ-027 - Audit Trail and Versioning](MIS-001/Requirement/REQ-027.md)**: All Aurora cards SHALL include an audit_trail with a per-card SemVer version, an optional SHA256 hash (nullable), and a chronological history of created/edited/deleted events including editor identity and RFC3339 timestamps.

- **[REQ-017 - Identifiers, Filenames, and Model Layout](MIS-001/Requirement/REQ-017.md)**: Aurora cards SHALL use stable identifiers (e.g., MIS-001) that MUST NOT change once issued. Card files SHALL be named <id>-<Sanitized_Name>.jsjson, where special characters are stripped and spaces are replaced with underscores. Models SHALL follow the Model Home and Mission folder layout conventions so tools can discover, validate, and render deterministically.

- **[REQ-022 - Canonical Relationship Registry](MIS-001/Requirement/REQ-022.md)**: Aurora tooling and documentation SHALL use a canonical registry of relationship verbs, including allowed source and target card types, to enable deterministic validation and interoperable views.

- **[REQ-024 - Schema Referencing Rules](MIS-001/Requirement/REQ-024.md)**: All Aurora card files SHALL include a $schema field referencing the applicable Aurora schema using a relative path from the card file to the Model Home schema file.

- **[REQ-019 - Directed Graph with Local Cycles](MIS-001/Requirement/REQ-019.md)**: All Aurora links SHALL lead away from the Mission card. Local cycles MAY exist within bounded subgraphs (for example state machines) as long as no link creates a path back to the Mission.

- **[REQ-018 - Single Root Mission](MIS-001/Requirement/REQ-018.md)**: Each Aurora model SHALL start with exactly one Mission card that serves as the root of the directed graph. The Mission card SHALL only have outgoing links and SHALL provide a consistent starting point for traversal and view generation.

- **[REQ-026 - Views as Projections](MIS-001/Requirement/REQ-026.md)**: Views SHALL be treated as projections of a single underlying model graph by selecting a set of card types (and optional subtypes) and rendering only those cards and the links between them; views SHALL NOT change the underlying model.

- **[REQ-020 - Boundary and Note Semantics](MIS-001/Requirement/REQ-020.md)**: Boundary cards SHALL be used to group related cards for rendering and navigation; they may have a subtype such as End to limit recursion. Note cards SHALL be used only as annotative leaves (incoming links only) and SHALL NOT introduce new structural model elements.

- **[REQ-021 - Canonical Card Registry](MIS-001/Requirement/REQ-021.md)**: Aurora tooling and documentation SHALL use a canonical registry of card types (and optional subtypes) to support consistent rendering, validation, and communication across tools.

- **[REQ-025 - Model Integrity Validation](MIS-001/Requirement/REQ-025.md)**: Aurora models SHALL be machine-validatable for integrity: every non-Mission, non-Note card SHALL have at least one incoming link; every card SHALL be reachable from the Mission; and all links[].target values SHALL reference an existing card id.
